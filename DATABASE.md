# SQLite database

Schema version 1 is bundled in `Sources/HungrySpotCore/Resources/001_schema.sql`; the first-run seed is `seed.sql`. `Database.bootstrap()` applies versions transactionally and records the one-time `initial_seed_complete` marker in the same transaction. Administrators' edits and deleted seed products are never reseeded. No user or default credentials are seeded: the first launch requires creating an administrator. Foreign keys are enabled on every connection. WAL and FULL synchronous commits are used for the live store. All currency fields are integer paisa; all dates are REAL Unix seconds. User-entered prices and amounts are limited to 9,999,999,999 paisa (Rs 99,999,999.99), consistently across editors and pricing.

## Column contract

- `schema_migrations(version INTEGER PRIMARY KEY, applied_at REAL)`
- `users(id, username UNIQUE NOCASE, password_hash BLOB, password_salt BLOB, password_iterations, role, is_active, created_at)`
- `categories(id, name, parent_id → categories, display_order, is_active, icon, image_path)`
- `products(id, name, category_id → categories, subcategory_id → categories, description, kind, base_price, image_path, is_available, is_active, display_order)`
- `product_variants(id, product_id → products, name, price, display_order, is_available, topping_price NULLABLE)`
- `deals(product_id PRIMARY KEY → products, needs_review, review_note)`
- `deal_items(id, deal_id → deals.product_id, label, quantity, requires_selection, display_order)`
- `deal_item_choices(id, deal_item_id → deal_items, product_id → products, variant_id NULLABLE → product_variants)`
- `orders(id, request_id UNIQUE, request_payload, order_number UNIQUE, type, status, created_at, cashier_id → users, cashier_name, customer_name, customer_phone, customer_address, notes, cancellation_reason, subtotal, delivery_charge, discount, total)`
- `order_items(id, order_id → orders, product_id → products, product_name, category_name, variant_name NULLABLE, unit_price, extra_price, quantity, notes)`
- `order_item_options(id, order_item_id → order_items, name, quantity, unit_price, product_id NULLABLE → products, variant_id NULLABLE → product_variants)`
- `payments(id, order_id UNIQUE → orders, amount, method, cashier_id → users, created_at)`
- `expenses(id, expense_date, amount, description, user_id → users)`
- `settings(key PRIMARY KEY, value)` — `app_settings` contains versioned-by-model JSON and `initial_seed_complete` guards initialization.
- `audit_logs(id, user_id NULLABLE → users, username, action, entity, details, created_at)`

The unprefixed names on order item fields are **historical snapshots**, not joins to the current menu. Every order stores its original cashier name and totals. Nullable option product/variant references preserve components used in deals, and prevent destructive deletion. Order item options store per-item component/extra quantities, with the parent quantity applied by presentation/reporting. Single payment per order is enforced by a UNIQUE constraint.

Product deletion rejects historical order/component references and bundle references (including archived bundles); archive instead. Variant removal rejects bundle and historical option references. Product variant child rows otherwise cascade when an unused product is deleted. Category deletion rejects children and assigned products. Accounts are deactivated rather than deleted. Passwords use PBKDF2-HMAC-SHA256, 600,000 iterations, a fresh 32-byte random salt and a 32-byte hash. Authentication uses a random in-memory session token mapped to an ID; each privileged operation reloads persisted role and active status. Logout, account mutation and restore invalidate applicable sessions. Database contents remain ordinary local SQLite; protect the Mac account and backups with OS disk encryption.

## Initial seed

9 main categories, 8 sections, 62 products (including 14 deals), 49 variants. Birthday bundles allow the seven explicitly special pizza flavours at Large size. Ordinary pizza deals have no inferred flavour eligibility and are marked for review; Deal 10 likewise requires Family Pan Pizza configuration. Seed SQL is generated by `scripts/generate_seed.py`, which also independently verifies counts, prices, choices and foreign keys in an in-memory SQLite database.

Indexes cover product names/categories, order dates/status/number, order line references, payment dates and expense dates. Transactions serialize on a recursive connection lock; nested transactions use savepoints. Backup uses SQLite's online backup API to capture committed WAL changes consistently. The destination is finalized in DELETE journal mode so the snapshot is self-contained and read-only validation does not introduce WAL/SHM sidecars. Existing destination files are rejected; unfinished snapshots are removed on failure.

`scripts/verify_persistence_sql.py` executes the shipped schema and seed, prepares literal authentication/catalog/audit SQL extracted from the services, and tests constraints, transactional rollback, the one-time seed marker, settings, search and standalone online backups using temporary SQLite stores. It does not execute Swift authorization or hashing. `AuthenticationTests.swift`, `CatalogTests.swift` and `DatabaseTests.swift` cover those native service behaviors and must run on macOS with the rest of the XCTest suite.

## October 2026 cashier update

No schema migration: schema version1 and seed bytes are unchanged. Historical PREPARING/READY/PAID values remain supported. New payment transactions set COMPLETED while inserting the payment and audits atomically. Cash tender and change are audit details only; payments.amount remains exactly the order total. New delivery numbers are normalized to local03 format; old snapshots are not rewritten.
